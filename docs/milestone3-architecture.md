# Milestone 3 impact plan

The implementation adds Doctrine Builder and modular product authoring to the existing offline workspace. It preserves the original bundled profile documents, migrations 001–003, projections v1–v3, revision history, explicit approvals, publication snapshots, and export provenance.

1. **Domain and storage.** Add strict schemas for doctrine lifecycle records, ordered module definitions, typed module content, operation layout overrides, rich documents, and assets. A doctrine lifecycle record wraps an exact configuration version; the published configuration remains in the existing immutable profile store. The family UUID, version UUID, numeric profile version, and human version label are separate identities. Drafts support optimistic editing; publication freezes their content. Retirement changes availability, not published content.
2. **Migration 004.** Add doctrine lifecycle and managed-asset tables with immutability guards. Module definitions are part of versioned profile documents; module instances and overrides are part of revisioned operation documents. No historical document is rewritten. Existing operation schema 1/2 receives an optional, explicitly versioned module-authoring extension only when used.
3. **Assets and portability.** Store immutable bytes in SQLite alongside strict metadata, SHA-256, and operation or doctrine-version ownership. SQLite backup therefore captures assets atomically. Portable `.ordo-doctrine` files use a bounded, strict JSON manifest with base64 assets, avoiding filesystem extraction entirely. Reject unsafe filenames, executable payloads, mismatched hashes, ownership errors, and identity collisions before a transaction persists anything.
4. **Rich text.** Use Tiptap in the presentation layer only. Store a restricted, versioned document tree with managed image IDs. The domain validates supported nodes, marks, links, nesting, and size. A deterministic exporter escapes text and attributes; it never accepts authored HTML. External images, scripts, handlers, and renderer implementation details are excluded from stored doctrine.
5. **Modules.** Provide a typed first-party library. Tables and matrices share typed columns/cells. Charts link to table and column UUIDs; timelines link to canonical event UUIDs plus numeric offsets. Canonical military modules consume existing entities. Registry mapping to React remains in the renderer. Unsupported optional modules show a finding; unsupported required definitions prevent publication/import.
6. **Layout and legacy content.** Doctrine definitions contain configuration, not planner content. Operation instances retain origin, definition binding, order, configuration override, timestamps, and removal state. Reset requires an explicit UI confirmation and retains removed/local content in recovery state. Existing generic and base-order content keeps its existing editor and compatibility view; no label inference or automatic conversion occurs.
7. **Projection and validation.** Add v4 and a module-aware HTML renderer. Existing projectors remain byte-for-byte unchanged. Track rendered module content, linked facts/table columns, and immutable asset references. Old records dispatch through their stored projection version. Validate domain bindings and asset ownership in save, publication, import, and restore paths; explain unresolved references without silently repairing authored data.
8. **User experience and verification.** Add a first-class Builder before operation creation, published-doctrine selection, ordered module authoring, and doctrine-first Responsible Staff controls. Preserve existing rename revisioning. Extend automated tests and actual Electron smoke coverage through a separate Milestone 3 script; retain all Milestone 1/2 coverage. Keep version 0.2.0 during development and advance to 0.3.0 only after completion and passing checks, then package and verify the release.

Rich editor reference: [Tiptap React installation](https://tiptap.dev/docs/editor/getting-started/install/react). No wider doctrine research is part of this milestone.

## Implemented boundaries and identity

The strict module extension has its own `schemaVersion: 1` and is optional on the existing doctrine/operation schemas. Legacy documents therefore keep their original shape until modular authoring is explicitly used. The doctrine lifecycle document wraps an exact `ResolvedConfig`; its family UUID, version UUID, profile version integer, human version label, and draft content counter serve distinct purposes. An operation continues to resolve its exact configuration pins through the existing repository API. A new doctrine version does not update those pins.

Bundled doctrine lifecycle entries are sidecars around the installed configuration. The original JSON documents are unchanged. Duplicating a doctrine creates a new family, preserves source citations, and copies managed doctrine assets to new immutable asset identities. Creating a new version retains the family and stable product/module identities while using a new version UUID. Draft edits use an optimistic content counter. Publication freezes the lifecycle row and installs its exact profile documents in the immutable profile store. Retirement is a separate append-only ledger entry, so it changes availability without rewriting published content.

`editorRegistry.ts` extends the renderer capability registry with all 17 first-party module types. Canonical unit and Signal capabilities reuse existing editors; report/distribution modules reuse the existing structured editor. Other modules use typed presentation dispatch. No React component names are serialized into domain configuration. Unsupported optional types remain readable with a finding; unsupported required types cannot be published.

## Persistence and recovery

Migration 004 adds `doctrine_versions`, `doctrine_retirements`, and `managed_assets`. Module definitions stay in validated profile documents; instances and layout overrides stay in immutable operation revision snapshots. There are no speculative tables for future military concepts. Saved module identity, origin, definition/product binding, and creation timestamp cannot be reassigned. Removed inherited modules remain explicit layout overrides.

Managed assets use SQLite BLOBs with immutable metadata, ownership, size, and SHA-256. The 10 MiB per-asset limit keeps this single-planner implementation bounded. Backup is the existing consistent SQLite backup, so metadata, bytes, history, doctrine, and pins are captured together. Restore validates schemas, ownership, hashes, profile/lifecycle agreement, historical bindings, and immutability triggers before replacing the active workspace. Doctrine export is strict JSON, capped at 64 MiB, with a canonical manifest hash and base64 assets; it does not extract archive paths. Asset import/export runs in the main process behind validated file commands and native dialogs.

Resetting a product layout requires confirmation. It restores inherited layout defaults, preserves authored content, archives operation-added modules for recovery, and retains the prior configuration override for explicit recovery. Removed columns do not destroy their stored cell values; unresolved field/column bindings are reported for the planner to resolve. No automatic content conversion or doctrine adoption occurs.

## Rendering, provenance, and validation

Projection v4 adds ordered module sections and records module selection/order, rendered content, linked canonical facts, chart source columns/data, and asset metadata. The Communications Card continues to use the established projection behavior. Historical exports dispatch using their recorded projection and renderer; v1-v3 and the original HTML renderer remain frozen. The v4 renderer is `html-v2`. Rich document rendering uses a restricted structured tree and an escaping formatter, with managed raster data substituted only after validation. Charts render deterministic SVG plus an accessible data table; no chart scripts are exported.

Publication still freezes a saved, explicitly approved operation revision with exact configuration. Applicability and module layout belong to that revision, independently from the source doctrine. Live previews derive from current canonical data. Publication preview derives from the frozen snapshot. Asset-storage errors are surfaced as findings and prevent approval/publication; malformed identity/binding data is rejected at save boundaries. Recoverable authoring issues such as a deleted chart column can be saved with findings without silently rewriting values.

Tiptap 3.31.4 is pinned and confined to the renderer. It supplies the React editor and structured document transactions; Ordo owns the domain schema, supported formatting, managed-image node, and deterministic export implementation. No remote runtime resources or executable custom modules are enabled.

## Windows release layout

Packaged output uses `release/${version}`. The existing `release/win-unpacked` application was open during release verification and Windows prevented replacement. Version-specific output avoids closing a planner session to build a new release. All three packaged smoke scripts resolve the executable from the current package version and use isolated data directories. Earlier installers remain in their original locations.
