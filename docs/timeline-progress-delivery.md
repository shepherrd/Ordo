# Visual timeline and planning progress

Delivery 2 of the connected planning implementation plan. Implemented and qualified on 15 October 2026. See [qualification evidence](timeline-progress-evidence.json).

## Behavior and decisions

- The Timeline shows shared operation events as duration bars or zero-duration milestones. View them in time order, grouped by assigned unit, or grouped by their existing responsible staff section. Phase and text filters, fit/day/week scales, horizontal scrolling, and a selected-event editor keep large schedules manageable. At most 60 event rows are mounted per page. Unscheduled events remain visible.
- Event links follow the predecessor automatically, as confirmed by the drafter on 15 October 2026. A link may follow the start or finish, with a signed minute offset. Finish links respond to duration changes. Cycles cannot be selected; save validation also rejects cycles and broken references. Removing a predecessor requires resolving its dependent event links first. Removing a unit remains protected by reference validation.
- Times are explicitly UTC. Durations are whole minutes, from zero to 525,600 (one year). Offsets in the editor range from minus to plus 5,256,000 minutes. The existing event identity, phase, staff owner, absolute time, predecessor, and offset remain authoritative.
- Planning progress lists the base order and actual authored attachments, with included products shown by default. It never creates unused doctrine products. Products are grouped in collapsible responsible-staff sections, using the existing doctrine/organization staff resolution. Filters cover staff, writing state, overdue products, text, and omitted/undecided products. At most 40 products are mounted per page.
- Content determines Not started or In progress; the drafter explicitly marks Ready, as confirmed on 15 October 2026. Product writing edits reopen that product. Following the [integration polish](connected-planning-integration-polish.md), changes to linked information reopen affected Ready products and show the reason. Unrelated facts and unselected card fields do not reopen them; card audience/phase changes do. Legacy orders that print shared fact tables still track those collections. Due-date and formal workflow-only edits do not reopen writing. Re-attestation after editing is preserved. Ready does not approve, publish, or complete an operational task.
- Due dates are optional UTC timestamps. A non-Ready product is overdue once its due date passes; the view refreshes this indication every minute. Open writing uses the existing product identity and navigation. Existing Search continues to open exact event/source fields, including a selected event outside the current chart filter/page.

## Persistence and compatibility

The optional versioned `event.schedule` extension stores duration, assigned unit, and predecessor start/finish anchor. The optional versioned `operation.planningProgress` extension stores only per-product due dates and explicit Ready attestations. Writing counts and resolved schedule times are derived. Old operation JSON is not rewritten to add empty extensions. No database migration is required: these additions live in the existing revisioned operation aggregate and its validated recovery/backup paths.

Historical snapshots without schedule metadata retain their original time resolution. Current time resolution handles the versioned finish anchor; existing relative timeline modules and explicitly selected event cards therefore follow the same source. Event cards offer optional Finish, Duration, and Assigned unit fields; these remain explicit authored card content. The schedule extension is recorded in card export dependencies when present. Existing retained HTML/PDF bytes and historical implementation fixtures remain unchanged.

Saved comparisons add a versioned timeline/progress supplement. New `review-html-v7` reports display duration, assigned-unit, relationship, resolved-time, due-date, and writing-ready changes. Verification recomputes this supplement from its retained endpoints; older report renderers are preserved. Planning-progress state is not added to operation-order output automatically.

The source baseline was copied before this delivery to `.test-data/timeline-progress-baseline-2026-10-15T21-38-14-285Z`. It preserves the actual development tree, including delivery 1 and all pre-existing modifications. Release `0.6.5` is not replaced by qualification candidates.
